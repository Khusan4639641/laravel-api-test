# MLM TZ Implementation Audit

Project: `/var/www/project7`
Branch: `safi-frontend-integration`
Date: 2026-06-04
Scope: audit only. Business logic was not changed in this phase.

Update note 2026-06-08: package/balance behavior was changed again. See `docs/MLM_BALANCE_RULE_UPDATE.md` and `docs/MLM_TZ_CALL_2026_06_07.md` for the current rule: package purchase/upgrade/manual assignment with business effects credits buyer main wallet by credited activity PV * 500 KZT; package price is still not PV.

Source requirement: `ТЗ: Правки MLM-логики Safi Life по итогам звонка` and explicit checklist from the task.

## Executive Summary

- Package matrix and manual package assignment are mostly aligned with current TZ: `PV != price`, START/VIP/ELITE activity/turnover PV are separated, ELITE turnover is 200 PV. Updated 2026-06-08: package assignment/purchase creates buyer wallet credit with current transaction types, not the old `package_activity_credit`.
- Critical business gaps remain: binary bonus has no 15-day calculation period, status is recalculated from `users.total_pv` instead of the small branch, status bonuses do not require ELITE package, and X2 uses only a flat first-line count instead of the 2/3 or 3/2 condition.
- Accountant access does not match the strict requirement “accountant only processes withdrawals”: accountant can read overview/transactions/orders/reports/withdrawals, but cannot approve/reject withdrawals.
- Several frontend pages read real API data, but some summaries are calculated client-side from currently loaded rows and some dashboard transaction/balance summaries are local calculations rather than backend summary contracts.
- Existing tests cover many recently fixed rules, but additional regression tests are required for the remaining gaps and for test fixtures that still use `pv = price` in unrelated helper factories.

## Services And Naming Notes

- `PackageActivationService` and `PackageUpgradeService` do not exist as separate services. Their logic is in `PackageService` plus `PackageActivationController` and `PackageUpgradeController`.
- `PvAccrualService` does not exist; current equivalent is `PvService`.
- `BinaryBonusService` and `ReferralBonusService` do not exist; current equivalent is `BonusService`.
- `NotificationService` does not exist; current implementation uses Laravel notification classes directly.
- This is not necessarily wrong, but tests and future tasks should reference actual classes unless the architecture should be split.

## Recommended Fix Order After Audit

1. Fix status eligibility foundation: calculate statuses from the small branch and define whether own package PV contributes to status at all.
2. Add ELITE-package gate to status bonuses and update tests accordingly.
3. Implement binary 15-day period semantics and decide whether calculation is manual, scheduled, or both.
4. Implement branch-distribution condition for X2: 2/3 or 3/2 among personally invited qualified partners.
5. Align accountant permissions with “only processes withdrawals”.
6. Revisit admin/dashboard balance labels so computed package activity amount is not confused with withdrawable wallet balance.
7. Clean up test fixtures that use `pv = price` where not explicitly intentional.
8. Add frontend tests for `/admin/partners` summary cards and dashboard summary mappings.
